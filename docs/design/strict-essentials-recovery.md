# Strict Essentials runner-loss recovery

**TLDR:** Persist encrypted ownership intent before any Cloud write and provide a separate authenticated read-only recovery discovery. Keep live qualification disabled while asynchronous tasks cannot be correlated conclusively.

**Date:** 2026-11-24. **Status:** Proposed. **Ticket:** RED-225344.

## Problem and scope

A hosted runner can disappear while a controller's Cloud create is pending. A local state file or an artifact uploaded only at the end of a job cannot recover that ownership. An empty inventory after runner loss cannot prove cleanup, because an asynchronous create may still finish. This change covers recovery evidence for the isolated Essentials case; it does not change product APIs or grant automatic cleanup authority.

## Design and security

Before any live operation, the workflow captures an authenticated account task-ID baseline and encrypts and uploads an immutable ownership-intent artifact with that baseline, run ID, attempt, exact run-owned names, tested commit, QA origin digest and an HMAC binding to the API account key. A missing, malformed or explicitly incomplete task list fails before upload or Cloud writes. AES-256-GCM uses a random nonce and a 32-byte key supplied by the private `QA_CHECKPOINT_KEY` Actions secret. The artifact contains no plaintext IDs or credentials. Keep the key available until every corresponding artifact and possible resource has been resolved; rotating it prematurely makes existing artifacts unreadable. The artifact expires after 90 days, so recovery must occur before expiry or use a separately retained encrypted copy.

The separate recovery workflow validates the originating completed dispatch and commit, decrypts and authenticates its artifact, requires the same independently verified QA origin and credential binding, and resolves exact names through authenticated GETs and complete database pagination. It prints no IDs. Duplicate or mismatched identities fail closed. An absent resource is **uncertain**, not clean. Existing foreign databases are reported as a count. The default workflow mode makes no Cloud mutations and never removes credentials or finalizers. The failed qualification remains failed after any recovery.

**Direct recovery is disabled.** A DELETE may have been accepted even when its task has not appeared in the account task list. A workflow rerun retains the same run ID, so observing only the two create tasks cannot safely authorize another DELETE. Both the hosted workflow and its CLI refuse direct recovery on all attempts until a durable pre-delete intent and replay guard are implemented and verified. Read-only inspection remains available; unresolved resources require manual investigation. The original live job's CR-only recovery is unchanged.

Redis Cloud exposes an account task list for recent operations and per-task details; processing completion can precede provisioning completion. Recovery reports the number of new and missing baseline task IDs and, when both exact resources exist, checks whether one new create task of each known Essentials kind independently reads back with the corresponding resource and parent IDs. Even matching tasks do not authorize mutation; both resource reads must also be active, and the candidate correlation has not been live-qualified. A listing that is incomplete, cannot correlate a request, or lacks an operation's ID cannot prove absence. [Redis Cloud task documentation](https://redis.io/docs/latest/operate/rc/api/get-started/manage-tasks/) and [request lifecycle](https://redis.io/docs/latest/operate/rc/api/get-started/process-lifecycle/) describe these limits. The controller's submitted task IDs are not durably recorded by the intent artifact, so task correlation and recovery mutation remain open. Cross-repository Cloud writes remain serialized by the coordinating session.

The authenticated [read-only preflight](https://github.com/RedisLabs/crossplane-provider-rediscloud/actions/runs/45289530988) observed the expected `tasks` array and its core fields in the QA account. Unknown response shapes fail the pre-write baseline and do not prevent read-only resource discovery.

## Validation, rollout and rollback

Credential-free tests cover ciphertext authentication, wrong key and source run, unverified endpoint, forced worker loss after simulated artifact persistence, ambiguous identity, and absent-resource uncertainty. The hosted checkpoint rehearsal uploads an encrypted intent, deliberately fails its producing job, then retrieves and decrypts the artifact in another job. The rehearsal is labeled in its authenticated payload and cannot authorize recovery. This simulates a failed job, not a forcibly lost host. Separate inputs on the existing dispatchable QA workflow invoke the reusable recovery workflow with a rehearsal-only guard: a strict source is rejected by that guard and a rehearsal source is rejected by normal source verification, so neither path can mutate Cloud. The coordinator must serialize live writers and record actual Cloud results. A real runner-loss and recovery mutation have not been qualified. Roll back by reverting this workflow and tooling; do not discard any outstanding encrypted artifact or key while run-owned resources may exist. No ADR or BDR is required for this testing-only change.
