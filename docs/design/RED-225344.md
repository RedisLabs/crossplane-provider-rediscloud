# AWS and GCP verification and usage documentation

Date: 2026-11-09.
Status: In progress; results belong to the verification ticket.
Ticket: [RED-225344](https://redislabs.atlassian.net/browse/RED-225344).

## TLDR

Verify provider commit `5ceb4431079b46fe79159b9ff637d4a3f1efb0e6` on an isolated
Kind cluster against a live non-production Cloud API. Run AWS Pro in `us-east-1`
and GCP Pro in `us-central1` sequentially, capturing active-state evidence before
normal deletion. Add a root [usage guide](../../USAGE.md) linked from the README.
Documentation edits are separate from the provider binary built for this run.

## Problem and goals

The README has short fragments but no complete create-to-cleanup walkthrough.
Existing acceptance checks do not by themselves provide an ordered, correlated
Kubernetes/API/console evidence set for both cloud providers.

The guide explains runner-side installation, credential storage, account lookups, Pro
subscription and database manifests, ACL rules, condition checks, connection
Secret keys, and child-before-parent deletion. AWS and GCP examples use the
existing CRD contract and no real credentials or account IDs.

## Verification behavior

- Record exact commit, package hash, runtime image ID, tool versions, and results.
- Run unit tests, lint/vet, generation/schema-drift, example validation, build,
  module verification, and the existing vulnerability gate.
- Kind hosts Crossplane core and its CRDs in GitHub Actions, never on the laptop.
  Cloud resources live in the QA account.
- Explicitly verify the QA API endpoint before requests; never fall back to the
  production API for this verification.
- Use a unique prefix per cloud. Require Ready and Synced, active Cloud status,
  and matching IDs. Capture trigger, Kubernetes status, live API JSON, console
  subscription, console database, and cleanup evidence in that order.
- Reuse existing acceptance functions through a local verification adapter,
  keeping the tested provider implementation unchanged. The adapter changes the
  Pro cloud/region, isolates the Kubernetes context and resource prefix, adds an
  evidence pause, and waits for deletion finalizers before removing credentials.
- Keep the controller and credentials until Cloud deletion and CR absence are
  independently verified. Document any retry, repair, failed gate, or evidence gap.

## Scope and limitations

The existing suite also covers ACL role/user and GCP Essentials create/delete.
GCP Essentials is distinct from GCP Pro. Neither a successful Pro smoke test nor
schema validation establishes update/import, Active-Active, networking, or Agent
Memory acceptance. Those gaps remain in [test-suites.md](test-suites.md).

No resource schema, runtime API, storage, business policy, or deployment
architecture changes are proposed here. No new ADR or BDR is needed. Existing
technical choices remain in [ADR-0001](../adr/ADR-0001-follow-upjet-v2.md).

## Security and operational impact

Live resources incur QA capacity/cost until deleted. Credentials remain in a
private local file and a Kubernetes Secret, never in repository files or evidence.
Logs and screenshots must be checked before attaching them to the dedicated
Crossplane ticket. RED-225329 is a separate Pulumi ticket and receives no evidence.

## Validation and rollout

Validate the usage guide's rendered YAML snippets against the checked-in CRDs,
check Markdown links, and review the guide against the actual run. Store complete
run results and remaining issues in Jira rather than claiming blanket readiness.
Rollout is documentation only; rollback reverts the guide and README links.

## Open issues from the implementation review

The existing QA harness needs explicit endpoint validation, failure cleanup that
retains credentials until deletion completes, Ready plus Synced assertions, and
Cloud/CR ID comparisons. This verification adds independent checks but does not
silently treat those harness changes as part of the baseline provider commit.
