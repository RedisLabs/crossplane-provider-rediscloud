# Shared QA account writer serialization

**Status:** Proposed; no lock implementation or deployment is established.

**Date:** 2026-11-24.

**Tracking:** RED-225344.

## TL;DR

The selected QA target is the existing account referenced by `UPTEST_CLOUD_CREDENTIALS`. Operator and Crossplane have independently verified that their current QA credentials target the same Cloud account. Pulumi's account identity has not yet been compared. A durable account-scoped coordinator and enforcement of its admission at the Cloud credential boundary are prerequisites to safely resume unattended writes. Repository-local workflow concurrency and point-in-time audits do not enforce that requirement. Existing cleanup must retain its ability to finish and the coordinator must keep an interrupted account occupied until cleanup is verified.

## Problem and current entry points

These are workflow observations on default branches at the date above, not a complete inventory of every human or external integration that may possess account credentials. A run on an older ref may execute older workflow code. Running jobs retain their original code.

Recoveries can themselves mutate the account. Direct Crossplane Cloud recovery is disabled; controller-led cleanup already in progress must not be stopped. A complete production inventory of other QA consumers and scheduled environment resets is required before claiming exclusivity.

## Goals and non-goals

Serialize every authorized Cloud writer to each verified account, preserve cleanup after failure or runner loss, and prove both properties without a Cloud writer before staged live rollout. Keep read-only diagnostics available. This design does not select or provision a store, assert Pulumi account identity, change secrets, authorize a lock bypass, or qualify any connector lifecycle.

## Proposed protocol

1. A trusted coordinator authenticates the workflow identity and maps its independently verified Cloud account identity to one opaque stable lock key. An unrecognized origin, account, workflow, source commit, or attempt is rejected. A run ID alone is insufficient: GitHub reruns retain the run ID and increment the attempt.
2. Acquire atomically with an owner record containing repository, workflow, run ID, attempt, commit, unguessable capability and monotonically increasing generation. A failed, lost, or ambiguous acquire response never grants permission to write. The record persists without automatic expiration. Competing acquires fail while ownership or cleanup state is unresolved.
3. Before each Cloud mutation, an enforcement point verifies current ownership and generation. A check in a client immediately before a request is insufficient by itself: the runner may pause after the check and resume after ownership changes. The preferred architecture is an authenticated mutation proxy that alone holds the Cloud write credential, checks the generation on every request, and prevents stale writers from reaching Cloud. Its admission and release protocol must also drain or resolve requests already admitted before release, including asynchronous Cloud tasks; checking only on entry cannot fence a request already in flight. If no proxy or Cloud-native fencing is available, no enforcement guarantee exists. Read-only clients may retain separately scoped credentials.
4. Persist encrypted run-owned resource identities and in-flight request/task intent before each mutation. Unknown request outcomes remain unknown. Recovery continues under the original ownership, with exact IDs and identity checks, never prefix-wide deletion. Only the specifically authorized recovery path can assume an interrupted owner after establishing the prior writer cannot continue; a new generation cannot by itself stop a client with an already issued static API key.
5. Release is an atomic, owner-and-generation checked transition only after authenticated complete inventory proves all resources owned by the run are absent, relevant asynchronous operations are terminal, and pre-existing resources remain intact. Incomplete pagination, identity mismatch, inaccessible task history, unknown API response, or inability to establish writer termination retains the lock and records a manual recovery state. No wall-clock timeout, job cancellation, or `always()` release clears it automatically. Account-specific standing resources are excluded only by an authenticated baseline and explicit ownership rules.

The proxy/coordinator must protect durable state across crash, restart and failover, and its storage ACL must prevent untrusted clients from changing or deleting ownership records or release evidence. Every Cloud write path, including controllers, Pulumi operations, recovery and old workflow refs, must be subject to the same enforcement. Otherwise this is cooperative scheduling, not a lock. Existing static credentials and old jobs require an audited transition: quiesce writers, verify and preserve outstanding cleanup, disable or revoke old write access where supported, and verify old refs cannot retrieve or use write credentials before enabling the new path. Never remove the credentials needed by an active cleanup job. How Cloud API credentials can be constrained or revoked is not yet established.

## Candidate implementation and crash boundaries (unapproved)

**Observed 2026-11-27:** Operator `redis_cloud_test` and Pulumi `QA nightly acceptance` workflows are disabled manually; Crossplane Nightly remains enabled but its scheduled standard path intentionally deferred before writing ([run](https://github.com/RedisLabs/crossplane-provider-rediscloud/actions/runs/45952378526)). Crossplane strict and comment-driven paths are not covered by that schedule gate, and the proposed additional gates in #48, #128 and Pulumi #22 remain open. Disabled workflow state, older refs, local credentials, console users and non-GitHub writers must all be audited before asserting exclusivity. Treat Pulumi as potentially sharing the account until identity is established.

The companion `scripts/qa_account_simulator.py` is a **non-writing local state-machine experiment** exercised only in GitHub Actions, not a deployed coordinator or proxy. SQLite is confined to one runner, and the experiment exposes no release operation and no Cloud transport. It is not an account lock or a credential boundary. The durable production store and Cloud credential controls must be selected and reviewed before integration. Do not interpret simulator results as proof of persistence or actual account exclusivity.

- Store one account record with an opaque owner identity, run ID **and attempt**, immutable baseline, generation, phase and a durable request-intent journal. Atomically compare-and-set `FREE -> ACTIVE`; an ambiguous acquire grants no write permission. A reconnect protocol must authenticate the identical workflow run and attempt, verify the existing binding and resolve the unknown result without admitting a second owner. Do not assume a GitHub run ID authenticates the client or that an OIDC claim identifies all checked-out code.
- The proxy must be the only holder of a usable account write credential. It defaults to denying all methods and paths except reviewed route/resource combinations. It atomically verifies the current owner and journals the exact request as `ADMITTED` before the upstream call; it disables automatic retries and records the resulting task and resource identities where available. All unexpected responses or interrupted forwards stay `UNKNOWN`. Baselines and release evidence are independently collected by the trusted service, not accepted as client assertions.
- On release, compare-and-set `ACTIVE -> DRAINING` before any cleanup inventory, close admission of new creates or updates, and wait for every admitted forward to resolve. Concurrent or late requests cannot reopen admission. Recovery has narrowly authorized cleanup for recorded run-owned resources while the same account remains occupied. An indeterminate create, task, partial inventory, failed authentication, proxy crash or unconfirmed previous executor termination retains the hold. Names or tags alone cannot establish ownership or authoritative absence.
- An unknown or ambiguously persisted admission closes new write admission and remains on manual hold: a point-in-time resource absence does not rule out a late accepted request. Any route to resolve it requires a verified definitive outcome, terminated prior executor and authoritative task and inventory evidence; if those are unavailable the hold persists. A proxy restart must not treat a persisted admission as unsent: the old process might have paused after validation and resume later. A replacement cannot send or release until its predecessor and any admitted upstream request are proven unable to act, or an actual Cloud-side fencing mechanism enforces generation. A single-replica setting or expired lease alone is not that proof. Asynchronous tasks must reach a verified terminal outcome and complete resource inventory before release.
- Credential migration is a hard rollout prerequisite: inventory all consumers, preserve any active cleanup, quiesce the old writers, then establish and validate an exclusive proxy credential and revoke old Cloud-side credentials through an approved process. Removing repository secrets alone cannot invalidate copies in old jobs, local files or controller Secrets. Confirm revocation and authorized access by read-only checks; any inability to establish exclusivity keeps unattended writers disabled. Read-only credentials must themselves have demonstrably read-only permissions or be mediated too.

Takeover may be possible if per-incarnation Cloud credential revocation is supported and demonstrably stops future requests, but that support and whether it affects already accepted tasks are unknown. A stopped container, a revoked repository secret, or a successful read-only 401 alone is not proof an earlier asynchronous task cannot later finish. Define one authorized drain initiator and at most one recovery executor, exact per-connector cleanup routes and an audited manual-hold procedure before rollout; retries and reruns need explicit ownership handoff. A break-glass path requires separate approval, prevents automatic release and must not assume a stale proxy has stopped.

CI-only verification must use independent client and proxy processes against a controllable fake store and fake upstream, with deliberate crash/restart at every durable transition; simultaneous acquire, response loss, stale proxy pause, drain-vs-create, duplicate recovery, lost upstream response, partial pages, ambiguous journal writes, release response loss, concurrent proxy incarnations and credential-revocation failure must remain fail-closed. Explicitly test cross-repository identities, stale refs, PR-code checkout and run attempts as untrusted inputs. A simulator cannot establish real GitHub identity claims, Cloud permissions, durable failover or task completeness; those remain separate staged integration gates.

## Alternatives and dependencies

- The existing `redislabsdev/github-actions-shared/actions/env-sync-pool` uses a Redis QA pool lock with a 9,000-second TTL and a force-override path. It is an existing environment-management service, but its expiration and override can allow a new writer while a previous Cloud mutation or cleanup remains unresolved. It is not suitable unchanged. Its Redis credential, ACLs, durability, usage authorization and access from the three connector repositories are unverified; do not reuse the credential or modify its pool.
- GitHub Actions concurrency is useful within one repository but does not supply a durable cross-repository account lock. A protected shared ref would still need verified atomic creation, no untrusted deletion or rewrite, durable history, and narrow cross-repository access. No such policy or approved GitHub App has been established. The existing one-shot recovery DELETE fence addresses a different problem and is not this account lock.
- A dedicated transactional store and proxy could enforce the protocol if approved and if both its durability and credential boundary are established. Existing GitHub-to-GCP workload identity documented for infrastructure deployment is scoped to that deployment repository, not evidence of authorization for these connector repositories or a suitable coordinator store.
- Separately owned QA accounts are an alternative to cross-repository serialization only when authenticated account identities are proven distinct, each account's credential access and writers are independently inventoried, and overlapping executions within each account are serialized. Account separation does not make prefix-based cleanup safe. A migration must preserve the old account's credentials and recovery path until its existing resources and tasks are reconciled, then eliminate stale writers to that account. Separate accounts, supported plans and permissions are not established for this effort.

Record the eventual durable architectural choice in an ADR after its owner, trust boundary, store and alternatives are evidenced. Do not mark the choice accepted merely because this proposal exists.

## Verification and rollout

Before any Cloud writer, use a credential-free fake broker/store and an isolated authorization rehearsal to prove: one winner under simultaneous acquire; run-attempt collision refusal; unknown acquisition response remains blocked; crash before and after intent, write and task completion retains ownership; stale generation and replay are denied at the mutation proxy; unauthorized release, premature cleanup release, missing pages, task uncertainty and foreign resources preserve the lock; a recovery actor can finish an old run without admitting a new writer; and only verified complete cleanup releases it. Test source-ref and OIDC constraints, denial of historical workflows and expired/revoked credentials separately. A fake store proves client logic, not service durability, credentials or authorization.

Integrate each connector behind its current fail-closed gate. Verify read-only preflight and in-flight cleanup separately. Obtain evidence for Pulumi account identity via an authenticated keyed comparison without exposing account IDs. Then audit all writer paths and credential access and rehearse forced runner loss. Once the approved store, proxy, policies, identity boundaries and recovery process are demonstrably enforced, run one bounded account writer at a time and verify exact resource cleanup before attempting concurrent admission. Roll back by reapplying the writer gates, leaving any active cleanup and lock in place; never delete an occupied lock to restore availability.

## Open questions

Which service and owner can provide an approved durable coordinator and appropriately restricted store? Can all Cloud writes be routed through a proxy and can old API credentials be revoked without harming other consumers? What are the authoritative complete account-task and inventory APIs? Do Pulumi credentials resolve to the same account? Which additional workflows, people or reset jobs can write it? What verified recovery procedure handles an indeterminate asynchronous task or unavailable owner?
