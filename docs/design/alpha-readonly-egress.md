# Alpha read-only lookup egress design

**TLDR:** The current route guard is fake-only and binds only loopback; it cannot authorize a QA lookup. Real installed-controller QA remains blocked until an enforced network boundary and its negative tests prove the controller cannot bypass the proxy.

- Date: 2026-11-25
- Status: proposed; no live QA credentials or requests
- Ticket: [RED-225344](https://redislabs.atlassian.net/browse/RED-225344)

## Problem and scope

Exercise Regions and PaymentMethod through the installed Crossplane package without permitting resource creation or mutation. Allowed Cloud operations are authenticated GET requests to exact `/v1/regions` and `/v1/payment-methods` routes. Existing account and credentials are inputs; account management and all live Cloud writes are excluded.

## Proposed boundary

The included prototype accepts only fake sentinel credentials, listens on `127.0.0.1`, and sends requests exclusively to a fake `127.0.0.1` upstream. It denies non-GET methods, alternate paths, query strings, bodies, non-sentinel credentials and non-200 responses; it never follows or forwards redirects. No headers, bodies, account IDs or credentials are logged. Hosted negative tests validate the proxy itself; they do not exercise the installed provider or network isolation.

A real-QA implementation needs a distinct, reviewed mode with a fixed independently verified QA HTTPS origin, credentials kept in a Kubernetes Secret, and no response/header/credential logging. It must never follow redirects, accept arbitrary destinations or forward disallowed methods, paths, or queries. A route guard alone is not an egress security boundary: a compromised or misconfigured provider could connect elsewhere.

## Mandatory hosted isolation proof before QA

1. Build and install the pinned #77 package in GitHub Actions Kind and record source, OCI digest, runtime image ID and artifact. A default Kind cluster alone is not evidence that NetworkPolicy is enforced.
2. Install a pinned network-policy-capable CNI with documented enforcement and prove its readiness. Configure provider-pod egress to the Kubernetes API and the reviewed proxy only; explicitly account for DNS, IPv4 and IPv6, proxy target IP changes, host networking and pod replacement. Permit proxy egress only to the verified QA origin. Deny everything else, including alternate Cloud origins and direct Cloud connections.
3. From the actual installed provider pod's network identity, prove the allowed proxy path works against a fake endpoint while direct fake-Cloud access, alternate egress and IPv6 bypass fail. Use controlled negative tests for POST, PUT, PATCH, DELETE, extra paths, encodings, queries, body, redirects and forbidden destinations. Confirm all deny results come from the enforcement boundary rather than an unavailable endpoint. Test policy after pod restart and replacement; no secrets are needed.
4. Validate the proxy's fixed-origin TLS, redirect denial, credential isolation, bounded errors and redaction using dummy data; independently verify complete request tracing. Only after all negative tests pass may a separately reviewed, GET-only QA run use the existing account. No resource lifecycle, cleanup API, or account management request is permitted.
5. Record exact source SHA, OCI digest, Actions run, CNI/version and sanitized request counts, negative results and controller status. Distinguish fake evidence from authenticated QA reads. Missing evidence, policy drift or uncertain network isolation means blocked.

### Node and rollout bypasses

Kubernetes explicitly permits traffic between a pod and its resident node regardless of NetworkPolicy; policies selecting a pod also combine additively. Neither a default-deny policy nor a policy-enforcing CNI alone proves that a provider cannot use a node-local relay. See the [Kubernetes NetworkPolicy semantics and limitations](https://kubernetes.io/docs/concepts/services-networking/network-policies/). The [Kubernetes SIG policy controller](https://kube-network-policies.sigs.k8s.io/docs/quick-start/) can enforce policies on a Kind cluster, but that capability is not proof that this exception is closed.

Before live credentials, the hosted proof must install an independently enforced node boundary, or establish another reviewed isolation mechanism, that denies provider-to-node relay traffic while preserving only the required API and proxy paths. The mechanism must be in place before the provider starts and must remain effective through policy convergence, node/pod restarts and replacement; it must not depend on an unverified interval after a pod is already running. Restrict who can change selectors, add permissive policies, use host networking, alter the proxy or modify the enforcement rules. Prove the provider pod's actual network identity and test a reachable node-local listener before and after enforcement, including alternate addresses and IPv6. A failure to connect is meaningful only if an independent control proves the listener is reachable. Also prove allowed proxy/API traffic still works. Preserve deny evidence without credentials or response content.

The Kubernetes API allowance is itself a potential relay: review and test the provider service account's effective permissions, including pod creation, exec, port-forward and service/pod proxy subresources, and prevent it from changing the policy or proxy. A successful network test does not establish those API authorization properties. A candidate node firewall must classify the provider before any credential is present, enforce both forwarded and node-local traffic, and fail closed if the pod IP, node, address family or firewall state changes. Static IP-only rules installed after startup do not satisfy this requirement.

The existing package test's ephemeral registry runs as a sidecar in the Crossplane pod. It must not be mistaken for a trusted general-purpose relay, and this installation topology cannot by itself establish the node boundary. Positive and negative probes, installed-provider identity, route enforcement and restart checks must all succeed in the same hosted run before any separate real-QA mode is proposed. The included fake proxy remains loopback-only and cannot be used as an installed-provider proxy as it stands.

The hosted OCI install workflow includes an initial, credential-free node-relay experiment. An ephemeral container in the installed provider pod uses its network namespace to reach a separately checked node listener; host INPUT rules then attempt to block that one listener port over IPv4 and IPv6, and service-account relay permissions are queried. This deliberately tests only an individual port and current pod identity. It is not an allowlist, startup or replacement proof, broad IPv6 test, policy-controller test, API-permission denial gate, proxy test, or authorization to use QA credentials. Any failed probe fails the job; an allowed API permission is reported as an open risk, not a successful security boundary.

A follow-on hosted experiment creates a dual-stack Kind cluster, verifies that the installed provider pod receives IPv4 and IPv6 addresses, and attempts the node-port probes in both families. Until hosted results pass, these are proposed tests; neither address assignment nor a single-port probe proves full egress containment. A future complete boundary must install default-deny rules before credentials are made available, scope them to an independently controlled workload identity that survives pod replacement, allow only the tested proxy and required Kubernetes API traffic, and validate both address families with independently reachable controls. It must also prove the effective service account cannot use API proxy, exec, pod creation, or policy changes to bypass that boundary. Keep the job fake-only until those tests and independent review succeed.

The next experimental hosted step uses pod-CIDR-scoped host INPUT and FORWARD rules on a disposable dual-stack node, allowing the Kubernetes API port and a fixed fake-only proxy port. The fake service has no upstream and accepts one GET route with synthetic credentials. The step attempts to test allowed GET, denied POST and independently reachable denied node listeners for each address family, then repeats those probes after the provider pod is replaced while the CIDR rules remain installed. This does not yet prove direct non-node traffic, actual controller lookup, the original pod's startup window, complete Kubernetes API authorization, or a production-quality boundary. A failing or missing check is not a pass; no real credentials or QA mode are available.

An initial guarded replacement reached ImagePullBackOff. A proposed mitigation mirrors the already-built fake package into a node-local registry, checks that its manifest hashes to the installed runtime digest, and points kubelet's registry mirror at it. The provider pod must still be denied access to that registry port. Hosted verification is required; the ImagePullBackOff root cause and mitigation have not yet been established.

The fake-only IPv6 experiment attempts a narrow Neighbor Solicitation exception: source pod CIDR, type 135, hop limit 255, and the solicited-node multicast address derived from the observed gateway. It must show the replacement uses that rule and that independently reachable non-NS echo and other node endpoints remain denied. The multicast address is derived from only 24 target bits; this rule does not inspect the ICMP payload or prove a unique gateway target, and it is not a production isolation boundary. Live credentials remain prohibited.

A follow-on fake-only probe places an independently reachable endpoint on the Kind bridge outside the node's network namespace. It attempts both address families from the actual original and replacement provider pods, requiring the CIDR deny and per-source accounting counters, plus a remove/reconnect/reinstate control. The bridge endpoint has no Cloud upstream. Results require hosted verification and do not cover every network destination, proxy bypass through the Kubernetes API, actual controller reconciliation, or original startup protection.

A further hosted-only experiment creates a provider configuration with synthetic credentials and a Regions lookup targeting the fake proxy. It attempts to require both a newly observed fake-proxy GET and the expected ready region status from the installed controller, before and after replacement; the replacement runtime image ID must match the original digest. These remain proposed tests until hosted execution and review pass. They exercise a fake service, not an authenticated Redis Cloud read, and do not resolve the remaining full egress, API-authorization, startup or multicast-target gaps.

The installed package in this experiment is built from pinned source `f2e4bbc86495d31eb2bed76ebe4124622150c80a`, not the separate integrated PR #81. The fake proxy's marker is an aggregate count of accepted GETs; it is not independent per-request source attribution. The test sequences its own debug requests before each count and requires fresh controller status, but must not describe that marker as a source trace.

The next hosted-only API audit impersonates the replacement provider service account with its standard service-account and authenticated groups. A temporary group-bound role and binding must change a previously denied fake-resource authorization to allowed and back to denied after cleanup. It also requires a positive Regions read authorization, samples relay and policy mutation permissions in every observed namespace plus selected cluster-scoped permissions, and attempts two direct proxy requests and a server-side dry-run pod creation expecting explicit Forbidden responses. Namespace inventory must remain stable during the audit. Name-constrained RBAC grants are not fully enumerated by unnamed reviews; direct proxy checks cover only the selected pod and service, and namespace stability does not prove RBAC remained unchanged. These checks run after the fake network experiment restores its rules and do not prove all Kubernetes API paths, token security, admission constraints, or startup-time isolation. A missing or incomplete authorization result fails the job; live QA remains blocked.

Both known calibration objects are independently deleted even if either cleanup fails. A timed-out create may leave an object whose generated name was never received; the job fails, and its disposable Kind cluster is discarded with the hosted runner. This is not a durable cleanup scheme for a shared cluster.

A fake-only startup experiment adds an init-container gate through a Crossplane DeploymentRuntimeConfig. The initial provider must remain stopped while the gate is closed and is released before the existing firewall experiment; this first release is not protected-startup evidence. For replacement, the test closes the gate before deleting the original pod, keeps the existing CIDR rules installed, tests the replacement init container's shared network while the provider runtime remains stopped, then releases the same pod and checks its immutable image ID and fake controller lookup. This is a proposed hosted test, not a live gate: ConfigMap updates, runtime configuration and node firewall require independent authorization, admission and drift enforcement, and the temporary removal controls occur only with synthetic data. A mutable gate alone is not a trustworthy security boundary.

## Operations and rollback

A separate proposed hosted Cilium experiment replaces Kind's default CNI, installs a fake namespace's selector-scoped egress deny before creating a selected probe pod, and checks the container's first scripted connection against an unselected-pod control and a same-pod connection after removing the policy. The failed connection is not independently attributed to Cilium policy: initial transient endpoint readiness is another possibility. This is an IPv4 synthetic endpoint and pod, not the installed provider, and the test cannot prove every packet or policy programming before first packet. Cilium's default mode may permit unresolved init identities; the experiment does not eliminate that race. The Cilium chart and Helm archives are SHA-pinned but signatures are not verified; chart-pinned agent/operator images and inherited Kind tooling remain separate dependencies. No real credentials, live QA, startup security or complete isolation are claimed. Hosted result is required.

A subsequent proposed admission experiment installs a Kubernetes ValidatingAdmissionPolicy before creating the Provider, rejects server-side dry-run matching pods lacking the exact fake gate or using a restartable gate sidecar, then requires the actual installed matching provider pod to start through that gate. This finite name-and-namespace policy is independently evaluated by the API server, but mutable administrators can change the policy, gate, credentials, workload names or RBAC. Other init containers can precede the gate or run as sidecars. It does not protect alternate workloads, demonstrate immutable identity, establish firewall enforcement before initial runtime startup, or authorize real credentials. The fake gate is still released before firewall installation. Hosted execution is required before claiming even this narrow admission behavior.

The fake-only guard cannot reach QA and has no credential path. Rollback removes the draft workflow and fixture. Production deployment and publication are out of scope. No shared-account lock is claimed; GET-only QA requires no Cloud writer, but any future mutation is blocked by the existing serialization and recovery requirements. Open questions: approved hosted CNI and image pins; enforced policy for this environment; verified QA origin; safe read-only selector and retention/redaction of status.
